Benchmark the application
===================================

**ID**: <a id="DS-004"></a>DS-004

**Related FFBDs:** [FFBD-004](/design/03_logical_decomposition.md#FFBD-004)

We can use uftrace and gcc flags `-g` and `-pg` to generate timeline of funcs. Compile code you want to benchmark:
```
❯ gcc -pg -g ~/Github/open_source_ebook_reader/docs/design/assets/ds_003_poppler_pipeline.c `MagickWand-config --cflags --cppflags` $(pkg-config --cflags --libs poppler-glib cairo glib-2.0 gio-2.0) `MagickWand-config --ldflags --libs` -o pdf_poppler
```

Record `uftrace` report:
```
❯ uftrace record ./pdf_poppler /mnt/sdcard/Operating_Systems_From_0_to_1.pdf ./output.png
```

So we can run the app with `uftrace record` then benchmark wich part of the code took how much time.

In this step it would be nice if we could just select a script and the script would do things like open an abook, wait until rendered, change page etc, so benchmarking wouldnt depend on person in the loop and their reflex. Then we just need to find pair of functions wiuch are interesting from benchmarking point like, callback called when we press button enter in menu and the func called when display is flushed, we can deduce this is the opening a book in some scenarios, it can be opening a library in others. Once we get the funcs pairs we can then write a script wich will based on stdout and `uftrace replay` can deduce how long took each phase of the flow.

The design:
1. Script waiting for first stdout.
2. Stdout happen so device boot itself.
3. Script record boot stages and their timing.
4. Device start ebook reader.
5. Script controll ebook reader according to scenario.
6. Application exits.
7. `uftrace replay` is flushed to stdout.
8. Script catch stdout and parse it into timeline.
9. Script find pairs of funcs and produce benchmarking raport showing how much each pair of funcs took + boot parts.
10. Raport and uftrace replay are produced by script for further inspection.
