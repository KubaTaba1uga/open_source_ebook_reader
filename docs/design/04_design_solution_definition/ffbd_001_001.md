## Recovery

We want to recover in case of power failure. Power failure may happen because we miscalculated battery level, and did not shutdown when the battery level was still enough to do so. The calculations may fail cause of bug, temperature change, battery chane etc. So let's design recovery mechanism especially for that.

To design data recovery mechanism we need to go back and design device persistence storage, bot are undisputely linked.

Let's split storega in two layers, the file system layer and the application layer.

Filesystem layer:
Storeage hardware -> device driver -> generic block layer -> filesystem.

Example of possible design of filesystem layer:
HDD -> SATA -> Linux generic block layer -> EXT2

Application layer:
OS File -> Data format -> data driver -> application.

Application layer:
/data directory -> JSON file -> Python json lib -> each file represent some part of device's state

### Filesystem layer

Consider simple experiment, we start with file containing one byte number:
```
0
```

We open a file, `lseek` to the end minus one byte and read a number `0`, we increment a number and append it to the file.
File content now looks like this:
```
01
```

Now we close the file.

And we repeat this procedure in infinty:
```
012
```

Then
```
0123
```

And so on and so on.

At some point we will cut the power of the board. 

If there is any data corruption we should see it based on the diturbed pattern.

Too make the scenario more real life like, instead of incrementing number we will append 128KB chunks of a number pattern like:
```
0123456789...
```

Then newline another chunk
```
01234567890123456789...
01234567890123456789...
```

And so on and so on.

The plan for experiment is like this, we boot up a board and check whether there is apropriate file, if there is a file we perform a check, if check is not succesfull we add +1 to corruptions and remove file, then we add +1 to attempts and start our app in the loop, we wait random interval between 3 and 10s and we kill board's power.

We do this for aproximetly 10 minutes. Then we check how many we have corruptions and how many attepmts, this should give us some measure about which filesystem corrupt most data on power failure.

Repeat few times, and check whether numbers are repeatable. We will compare our filesystems to ext2 and will see whether we can do better or worse in:
- number of corruptions (how often we need to discard file cause of data corruption in pct)
- speed in continous write (how much blocks we manage to write in number per second, until corruption occured)
- recovery time (TBD)
- storage penalty (experiment TBD)

Recovery file system layer:

- what storage overhead journal enabled add on disk (data, metadata) in PCT
- what speed overhead journal enabled add on disk (data, metadata, ordered, unordered)
- what speed overhead checksum enabled add on disk (data, metadata, ordered, unordered)
- what if block is skipped? this means our data is corrupted?
- journal only protect data integrity in case of sudden powerloss, 
  it does not protect against data degradation like malfunctioning hardware (do we need the latter?)
- data=journal does not support chesums, why? what does it mean?
  Ext4 computes checksums for structural metadata like inodes, block bitmaps, and extent trees.
  The JBD2 journal layer does use checksums, but these only protect the integrity of the journal blocks themselves (ensuring the journal log isn't corrupted or torn during a crash).
  dm-integrity? This help in detecting stuff like bit rot, for our use case, we do not care. This is just ebook reader data, no some bank financial records. SQLITE should handle this.
- Checkpointing: Periodically, F2FS writes a consistent snapshot of its metadata to a checkpoint area. After a sudden power loss, the file system simply rolls back to the last valid checkpoint.  






Recovery sqlite layer:
- Write-Ahead Loggi  ng support chesums for transactions.
  When SQLite opens the database after a crash, it reads the WAL file sequentially, verifying the checksum of each frame. If a power loss interrupted a write, the final frame in the log will be truncated, zeroed out, or corrupted. Its checksum calculation will fail.
  SQLite detects the first frame with an invalid checksum, recognizes it as the cutoff point of the crash, and silently ignores all subsequent frames in the WAL file. The database safely rolls back to the last fully verified, consistent state before the crash.
  https://avi.im/blag/2025/sqlite-wal-checksum/ https://avi.im/blag/2024/sqlite-bit-flip/ https://www.recoveryfix.com/blog/repair-corrupt-sqlite-database/#:~:text=FAQs%3A%20Before%20You%20Ask%2C%20Read%20This!%20Q%2D,method%20to%20fix%20a%20corrupted%20SQLite%20database.
  
  So once again this just ensure that if we have sudden data loss we will go back to the last working checkpoint. I think this is good enough.
  By default If a bit-flip happens to alter a structural pointer, cell offset, or header byte in a way that breaks the B-tree layout, running PRAGMA integrity_check; will immediately detect the anomaly and report an error (such as malformed database page). But this won't support stuff like PNG bit flipped, so default behaviour can make device in some wierd half working state. 
  Full Bit Rot Protection: The Checksum VFS Extension. This can work in theory but there is no way to validate all data other than just read it all and ensure no error. The read will take more time the more pages we rendered and the more books are in the system. I think we should drop bit-rot and just ensure sudden power loss is covered.
