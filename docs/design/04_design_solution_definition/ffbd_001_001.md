## Recovery

We want to recover in case of power failure. Power failure may happen because we miscalculated battery level, and did not shutdown when the battery level was still enough to do so. The calculations may fail cause of bug, temperature change, battery chane etc. So let's design recovery mechanism especially for that. We want to ensure that in case of sudden power loss we are able to recover to the last moment where data was still valid.

To design data recovery mechanism we need to go back and design device persistence storage, bot are undisputely linked.

Let's split storega in two layers, the file system layer and the application layer.

Filesystem layer:
```
Storeage hardware -> device driver -> generic block layer -> filesystem.
```

Example of possible design of filesystem layer:
```
HDD -> SATA -> Linux generic block layer -> EXT2
```

Application layer:
```
OS File -> Data format -> data driver -> application.
```

Application layer:
```
/data directory -> JSON file -> Python json lib -> each file represent some part of device's state
```

### Filesystem layer

Consider simple experiment, we start with file containing one byte number:
```
0
```

We open a file, `lseek` to the end minus one byte and read a number `0`, we increment a number and append it to the file.
File content now looks like this:
```
01
```

Now we close the file.

And we repeat this procedure in infinty:
```
012
```

Then
```
0123
```

And so on and so on.

At some point we will cut the power of the board. 

If there is any data corruption we should see it based on the diturbed pattern.

Too make the scenario more real life like, instead of incrementing number we will append 128KB chunks of a number pattern like:
```
0123456789...
```

Then newline another chunk
```
01234567890123456789...
01234567890123456789...
```

And so on and so on.

The plan for experiment is like this, we boot up a board and check whether there is apropriate file, if there is a file we perform a check, if check is not succesfull we add +1 to corruptions and remove file, then we add +1 to attempts and start our app in the loop, we wait random interval between 3 and 10s and we kill board's power.

We do this for aproximetly 10 minutes. Then we check how many we have corruptions and how many attepmts, this should give us some measure about which filesystem corrupt most data on power failure.

Repeat few times, and check whether numbers are repeatable. We will compare our filesystems to ext2 and will see whether we can do better or worse in:
- number of corruptions (how often we need to discard file cause of data corruption in pct)
- how many data was saved before power losss (how much blocks we manage to write in number per second, until corruption occured)

Most filesystems support recovery mechanism built into the filesystem, to ext2 we will use fsck as recovery. To repeat experiment look into `docs/design/assets/ffbd_001_001*` files.

| Filesystem | Corruptions (1st run) | Corruptions (2nd run) | Corruptions (3rd run) | Speed (1st run) | Speed (2nd run) | Speed (3rd run) |
| --- | --- | --- | --- | --- | --- | --- |
| **EXT2 no fsck** | 100% | 91% | 97% | 7897365 bytes/s | 6372972 bytes/s | 5935717 bytes/s |
| **EXT2 fsck** | 76% | 76% | 62% | 7700757 bytes/s | 8541033 bytes/s | 7940483 bytes/s |
| **EXT4 metadata journal** | 71% | 71% | 68% | 4294718 bytes/s | 4371544 bytes/s | 4368500 bytes/s |
| **EXT4 data journal** | 0% | 0% | 0% | 5803558 bytes/s | 6071203 bytes/s | 6260314 bytes/s |
| **EXT4 writeback journal** | 62% | 78% | 71% | 4577387 bytes/s | 4569316 bytes/s | 4601567 bytes/s |

```
sudo mkfs.ext2 /dev/sdd6 && sudo e2label /dev/sdd6 data && sudo mount /dev/sdd6 /mnt/usb/ && sudo tar -xvpzf ~/partition_backup3.tar.gz --numeric-owner -C /mnt/usb/ &&  sudo umount /dev/sdd6
```

Ext4 metadata journal flash cmd:
```
sudo mkfs.ext4 /dev/sdd6 && sudo e2label /dev/sdd6 data && sudo mount /dev/sdd6 /mnt/usb/ && sudo tar -xvpzf ~/partition_backup3.tar.gz --numeric-owner -C /mnt/usb/ &&  sudo umount /dev/sdd6 && sudo tune2fs -O has_journal /dev/sdd6 && sudo tune2fs -o journal_data_ordered /dev/sdd6 && sudo e2fsck -y -f /dev/sdd6; sudo tune2fs -O ^metadata_csum /dev/sdd6 
```

Ext4 data journal writeback flash cmd:
```
sudo mkfs.ext4 /dev/sdd6 && sudo e2label /dev/sdd6 data && sudo mount /dev/sdd6 /mnt/usb/ && sudo tar -xvpzf ~/partition_backup3.tar.gz --numeric-owner -C /mnt/usb/ &&  sudo umount /dev/sdd6 && sudo tune2fs -O has_journal /dev/sdd6 && sudo tune2fs -o journal_data_writeback /dev/sdd6 && sudo e2fsck -y -f /dev/sdd6; sudo tune2fs -O ^metadata_csum /dev/sdd6 
```

Ext4 metadata and data journal flash cmd:
```
sudo mkfs.ext4 /dev/sdd6 && sudo e2label /dev/sdd6 data && sudo mount /dev/sdd6 /mnt/usb/ && sudo tar -xvpzf ~/partition_backup3.tar.gz --numeric-owner -C /mnt/usb/ &&  sudo umount /dev/sdd6 && sudo tune2fs -O has_journal /dev/sdd6 && sudo tune2fs -o journal_data /dev/sdd6 && sudo e2fsck -y -f /dev/sdd6; sudo tune2fs -O ^metadata_csum /dev/sdd6 
```

At this point EXT4 with journal=data is clear winner. 

F2FS with enabled checkpoints:
```
sudo mkfs.f2fs -f -l data /dev/sdd6 && sudo mount /dev/sdd6 /mnt/usb/ && sudo tar -xvpzf ~/partition_backup3.tar.gz --numeric-owner -C /mnt/usb/ &&  sudo umount /dev/sdd6
```
Issue with adding F2FS to comparison is that F2FS by default run checkpoint on 60s interval or when we do fsync, because of how our test is structured it is really hard to tests F2FS, we do not fsync at all and our test time is less than 20s. So to see comparison where `fsync` is used look into `Filesystem layer + sqlite` section. 

Conclusion at this point is simple, if we do not call `fsync`, only safe filesystem is ext4+data=journal. 

### Storage performance

To test storage io we use fio. We use `psync` io engine, because it uses `pread` and `pwrite` functions exactly like sqlite (in src/os_unix.c). 

Sequential read:
```
fio --name=seq-read --filename=/mnt/testfile --size=1G --direct=1 --ioengine=psync --iodepth=1 --runtime=60 --time_based=1 --rw=read --bs=1M > seq-read.log 2>&1
```

Sequential write:
```
fio --name=seq-write --filename=/mnt/testfile --size=1G --direct=1 --ioengine=psync --iodepth=1 --runtime=60 --time_based=1 --rw=write --bs=1M > seq-write.log 2>&1
```

Random read:
```
fio --name=rand-read --filename=/mnt/testfile --size=1G --direct=1 --ioengine=psync --iodepth=1 --runtime=60 --time_based=1 --rw=randread --bs=4k > rand-read.log 2>&1
```

Random write:
```
fio --name=rand-write --filename=/mnt/testfile --size=1G --direct=1 --ioengine=psync --iodepth=1 --runtime=60 --time_based=1 --rw=randwrite --bs=4k > rand-write.log 2>&1
```

Show raports stats:
```
grep -H "bw=" *.log | awk '{printf "%-22s %s\n", $1, $3}'
```

| Filesystem                              | Sequential read | Sequential write | Random read | Random write |
|:----------------------------------------|----------------:|-----------------:|------------:|-------------:|
| EXT4 `data=journal`                     |      22.6 MiB/s |        4.6 MiB/s |   5.0 MiB/s |    2.2 MiB/s |
| F2FS                                    |      22.3 MiB/s |       12.4 MiB/s |   5.8 MiB/s |    1.2 MiB/s |
| F2FS `max_roll_forward_node_blocks=100` |      22.3 MiB/s |        8.6 MiB/s |   5.3 MiB/s |    1.3 MiB/s |

`mrfnb` means max_roll_forward_node_blocks, without this feature we are unable to pass any crash tests.

By default `sqlite` usage patter looks more like `Random write` and `Random read`. 
There is `SQLITE_ENABLE_BATCH_ATOMIC_WRITE` wich can convert some of the `Random write` to `Sequential write`, but it can only work on F2FS. 

```
sqlite3 /path/to/your.db "PRAGMA integrity_check;"
```


### Filesystem layer + `sqlite`

Problem with performance benchmarks is that we can see that ext4 is better with random write while F2FS is better with sequential write. I think that we will often read and write pages to the db to optimize user expirience, book page for a screen 1872x1404 is around 320 KB=(1872*1404/8)/1024. So i supose for our case the sequential read and write is more important. Goal here is to ensure that with appropriate sqlite settings f2fs or ext4 with journal=data will be significantly faster than the other in writing and reading sequential data. Based on the Storage performance section one can assume that f2fs will be faster. We will use F2FS `max_roll_forward_node_blocks=100` to keep recovery time resonable.

From what i read main performance related decision in sqlite is whether use journal_mode=WAL or journal_mode=DELTE, here are tests settings for WAL:
```
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL
```

Here for DELETE:
```
PRAGMA journal_mode=DELETE;
PRAGMA synchronous=FULL;
```

We choose this settings cause of the table in `sqlite` docs (PRAGMA schema.synchronous):

| Rollback Mode | DELETE Mode          | WAL Mode          |
|---------------|----------------------|-------------------|
| EXTRA         | ACID                 | ACID              |
| FULL          | Maybe not durable    | ACID              |
| NORMAL        | Maybe not consistent | Maybe not durable |
| OFF           | Not consistent       | Not consistent    |

We just need consistancy, if we loose a commit or two on powerloss, it does not really matter. It is just an ebook after all.

There is also compile option `SQLITE_ENABLE_BATCH_ATOMIC_WRITE` wich works only on F2FS, so we add it to the test.

|------------------------------|-------------|-----------------| ----------- |
| **EXT4 meta journal DELETE** | 0%          | 60 inserts/s    | 1104 rows/s |
| **EXT4 meta journal WAL**    | 0%          | 60 inserts/s    | 1142 rows/s |
| **EXT4 data journal DELETE** | 0%          | 21 inserts/s    | 1098 rows/s |

| **F2FS ATOMIC DELETE**       | 0%          | 66 inserts/s    | 1104 rows/s |
| **F2FS ATOMIC WAL**          | 0%          | 51 inserts/s    | 1142 rows/s |

### Conclusions 

Based on the benchmark we choose `F2FS ATOMIC DELETE`, as it provide best overall write speeds and reasonable read time.

Filesystem layer:  
SD Card -> eMMC -> Linux generic block layer -> F2FS

Application layer:  
/data/ebk.db -> SQLite -> sqlite3 -> each table represent some part of the device's state.
